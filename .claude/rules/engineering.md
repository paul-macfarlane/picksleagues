# Engineering Rules

Standards for all code in this repo. When a rule and `docs/architecture.md` conflict, the architecture doc wins for architecture; these rules govern craft. Violating a rule is fine only with a stated reason.

**Every rule here states the failure it prevents.** A rule whose justification is "it's cleaner", "best practice", or nothing at all is not a standard — it's a preference wearing a uniform, and it costs real judgement at every review to enforce. If a rule's *why* can't be written in a sentence naming what goes wrong without it, delete the rule. This applies to rules already in this document, not only new ones.

## Architecture & boundaries

- **API-first.** The SPA consumes the generated OpenAPI client (`openapi-fetch`) only — never hand-rolled `fetch` against API routes, never types duplicated from the server. A hand-rolled call is a second contract nobody regenerates, so a schema change breaks it at runtime instead of at build. Anything a future mobile client couldn't do through the contract is a design smell.
- **SPA data bindings live in `apps/web/src/api/<domain>.ts`, not in components or routes.** Each domain module owns its query keys, query hooks, and mutation hooks (invalidation fan-out, wire-slug → toast copy); hooks call the generated client directly inside — no additional wrapper restating endpoints (that's the client-side repository-layer smell). UI files render and wire: zero direct `api.*` calls, zero query-key literals — a key written in a component is a key the mutation's invalidation fan-out doesn't know about, and it fails as a stale view nobody traces back to the file that caused it. Auth flows go through the Better Auth client and are exempt.
- **One definition per DTO.** Zod schemas in `packages/schemas` are the single source for runtime validation, OpenAPI generation, and TS types. No parallel interfaces restating a schema. Username rules, settings shapes, and enums live here so the same rule serves API and UI.
- **Route handlers are thin boundaries:** validate (zod via `@hono/zod-openapi`) → auth/role guard → delegate to a domain service. No business logic or DB access inline in a route handler or job endpoint — logic living in a handler can only be exercised through HTTP, and the next handler needing the same rule reimplements it rather than importing it.
- **Route plumbing is shared, never copy-pasted.** OpenAPI error-response descriptors (401/403/404/500), the deps guards (`requireDbAndClock`/`requireSession` middleware), and the unhandled-error handler (`app.onError` → logged JSON 500) live in `apps/api/src/lib` — a route file never restates them. Expected refusals travel as typed service results the handler maps explicitly, with **TypeScript enforcing coverage** so adding a reason is a compile error — either an exhaustive `switch` in the handler, or a lookup keyed by the reason union (`as const satisfies Record<Refusal, …>`), which is the better form once the same refusals are mapped from more than one route file (`lib/pickem-refusals.ts`). Anything *thrown* is a bug by definition and becomes the logged 500 — except framework-thrown `HTTPException`s (e.g. Hono's malformed-body 400), which are typed client refusals and pass through. Wire error slugs come from the `ERROR_CODE` const set in `packages/schemas`, never inline strings.
- **A service names its refusal reasons in a const set; it never names an HTTP status.** Which const set is settled by whether the reasons and the wire codes are the same list. A service whose refusals map 1:1 onto `ERROR_CODE` returns those values directly (`admin-overrides.ts`) — inventing a parallel vocabulary to alias them one-for-one buys nothing. A service whose refusal set *diverges* from the wire — a reason with no code of its own, one code at two statuses, or a set several route files map — gets its own set plus a `lib/*-refusals.ts` mapping module (`PICKEM_REFUSAL`). Both keep HTTP out of the service, which is what lets a job, a sim endpoint, or a second route reuse the rule; a service that returns 409 can only be called from the one handler that speaks it. Pick by which one the reason list actually is, and don't mint a mapping module for a two-reason service a single handler maps.
- **Services own their queries — no repository layer.** Domain services call Drizzle directly; Drizzle is already the typed data-access abstraction, and services taking `db: Db` compose into transactions naturally (a `tx` satisfies `Db`). A non-trivial query needed by two services gets extracted as a shared function — a targeted extraction, not a layer. The testing seams are integration tests against real Postgres and the pure `packages/scoring`, not mocked repositories.
- **`packages/scoring` stays pure.** Settlement/scoring functions take plain data and return plain data — zero I/O, no imports from `db` or `core`. This is the most intricate logic in the app and the reason it's exhaustively testable.
- **Provider shapes never leak.** ESPN response shapes live inside the ESPN adapter in `packages/core`; everything else sees only our domain types via `GameDataProvider`. Swapping providers must touch one module.
- **Request paths never call ESPN.** External data is ingested by jobs into our tables; reads serve our tables. An ESPN outage degrades ingestion, never the product.
- **Per-mode pick, result, and standings tables, not polymorphic ones** (arch D9, amended by ADR-0016). A new mode adds its own `<mode>_picks` / `<mode>_pick_results` / `<mode>_standings` plus a settings schema and a scoring module. Genuinely shared: `games` (which now carries the current spread directly — SIMP-7 collapsed `odds_snapshots` into `games.spread`), the league/membership tables, and the *pure* ranking core in `packages/scoring`. Never add a nullable per-mode FK plus a one-of `CHECK` to make one table serve two modes — that's the polymorphic swamp D9 rejected, relocated downstream.
- **Mode-specific surfaces are named for their mode; generic names are reserved for genuinely mode-agnostic ones.** A Pick'em-shaped table, Zod schema, OpenAPI component, service, route path, query key, or component is `pickem*` / `/leagues/{id}/pickem/…`, so Elimination and March Madness get symmetric homes instead of the first mode to ship squatting the unqualified name. Before giving something a generic name, name the second mode that will use it unchanged — if you can't, it's mode-specific. Shared today: `PICK_OUTCOME`, `PICK_TYPE`, `GET /weeks/{id}/games`, `GET /leagues/{id}/weeks`, `packages/scoring/src/standings.ts`.
- **A file that accretes unrelated responsibilities gets split** along those responsibilities — unrelated concerns sharing a file route every change through it, so it collects the merge conflicts, the review noise, and the obligation to read the whole thing to change a tenth of it; conversely, don't mint a new module for a lone function an existing domain module already covers.

## Time & locking (the load-bearing rules)

- **All "now" reads go through the injected `Clock`** — no raw `Date.now()`, no `new Date()` for current time, no SQL `now()` in domain logic (lint-enforced). Under the simulator a wall-clock read puts one branch of the code in a different year from the rest of the app, and it surfaces as a lock that won't lift rather than as an obvious clock bug. Clock values reach SQL as bound parameters.
- **The SPA has a clock too, and it is the server's** (`apps/web/src/lib/app-clock.ts`). Any label phrased relative to now reads `useAppNow()`, never `Date.now()` — under the simulator the browser sits at a different instant, so a browser-clock label contradicts the very lock states the API computed. The lint rule above does not cover `apps/web`, so this one is on review. The store learns the offset where a `/me` response lands, which is the only moment the browser's clock is a valid reference for the server's; components must not re-derive it.
- **Lock state is derived, never stored** (arch D11): reads compute `locked = kickoff_at <= clock.now()`; every pick mutation re-validates `kickoff_at > clock.now()` inside its transaction and returns 409 on violation. No `locked` columns, no lock-flipping jobs — a stored flag is wrong for as long as the job meant to flip it is late, and a rescheduled kickoff leaves it wrong until something remembers to rewrite it.
- **Pick visibility is enforced in the query layer** — pick rows are serialized to non-owners only after the associated game kicks off. Never client-side filtering, never a visibility flag column: a filtered client has already received the rows, so the leak is in the response and a devtools tab is enough to read a rival's picks.
- Join cutoffs and commissioner power windows (pre-start vs post-start) derive from the same clock + game timestamps — a second notion of "now" would admit a member to a league whose first game the API already considers locked.

## Data & database

- **Constraints encode the rules.** One membership per user per league, unique team per member per league (elimination), exactly 63 slots per bracket, citext-unique usernames — the DB enforces what the spec states; app-level checks are a second line of defense, not the only line, because an app-level check races: two concurrent joins can both read a league as under its cap.
- **Use transactions for multi-step writes** that must be atomic (settle + rebuild standings, join + cap check) — a half-applied settle leaves standings that no recompute would reproduce. Prefer collapsing a check-then-act into one guarded statement where possible. Never hold a transaction open across a network call: it converts someone else's timeout into lock contention and connection exhaustion here.
- **Settlement is a pure derivation** (arch D10): every mode's result and standings tables (`pickem_pick_results`, `pickem_standings`, and their per-mode siblings) must be recomputable from (picks, results, settings) at any time. The incremental path is an optimization; never write state a full recompute wouldn't reproduce.
- **Jobs are idempotent** — safe to re-run, safe to double-trigger, safe to fire manually from the admin page. A missed tick means the next tick does the work; no job may depend on having run exactly once.
- **Override precedence is `override_* ?? provider_*`**, resolved in exactly the places the architecture names (serializers + settlement input loader). Ingestion writes only provider fields; a re-sync can never clobber a correction. Every override writes `admin_audit`, in the same transaction as the write it records, capturing the prior value. An admin rebuild does the same inside the recompute's own transaction, its prior value being the summary of the derived state about to be wiped (result and standings row counts plus their last-write instants) — the rows themselves are a derivation arch D10 already defines as reproducible, so copying them would bloat the trail without answering the only question it is asked: what stood there, and when had it last settled.
- **Settings JSONB evolves additively.** A change to a per-mode league-settings schema must either be additive with a Zod `.default()` (so previously stored rows still parse) or ship a data migration rewriting the stored JSONB — never let stored settings and the current schema silently diverge. Read paths that feed scoring/settlement parse through `LEAGUE_SETTINGS_SCHEMAS` so defaults materialize instead of being trusted to exist.
- **Constraint-violation detection goes through the shared `isUniqueViolation` helper** (`packages/db`) — never restate the DrizzleQueryError → pg `DatabaseError` unwrapping inline, because an inline copy stops matching silently when the wrapping changes and an expected conflict becomes a logged 500.
- **Validate all external input** with a schema before use — route params, query params, bodies, job payloads; unvalidated input reaches the query as whatever the caller sent, and the failure surfaces as a 500 deep in a service instead of a 400 at the edge. Validate env vars once at startup. `APP_ENV` gates simulator routes by **non-registration** in production, not by auth.

## Contract & codegen

- The OpenAPI spec and generated web client in `openapi/` are **committed**; CI fails if regeneration dirties them, because a stale client is a SPA type-checking green against an endpoint the API no longer serves. Change the Zod schema → regenerate → commit schema, spec, and client together.
- **Never wrap an `.openapi()`-registered schema in `.nullable()` (or `.optional()`) inline** — the wrapper inherits the registration, and the first one to register wins, so `null` gets folded into the *shared component* and silently widens every other `$ref` to it. Register the nullable variant under its own component name instead (`NullableUsername` in `packages/schemas/src/me.ts`, `NullableSimScenario` in `sim.ts`). This fails silently — `pnpm contract:check` stays green because the spec is self-consistent; only the generated client's types are wrong.

## Quality

- **TypeScript strict.** No `any` without a written reason; no `@ts-ignore` without a comment explaining why — an unexplained escape hatch is indistinguishable from a deliberate one, so nobody dares delete it and the hole outlives the problem it was opened for.
- **Value sets are const objects** + `as const` with a derived literal-union type (game status, league mode, pick outcome, member role, push/tie resolution, league actions, wire error codes). The TS `enum` keyword is banned: it isn't erasable syntax, so it emits runtime code every transpiler in the chain has to agree to keep, and it types nominally — a string equal to a member isn't assignable to it, which is exactly the assignability the const-object pattern relies on. Non-test code never compares raw literals of a set; tests MAY assert raw literals — they pin the contract so a constant-value edit fails loudly.
- **Comments explain why, never what.** State constraints, invariants, cross-file couplings, and ADR/architecture refs; delete sentences that restate the signature or narrate steps — a comment narrating the code is a second copy of it that no compiler keeps honest, and it starts lying the first time the code moves.
- **A comment cites durable identifiers, never a work package's internal numbering.** `ADR-0009`, `arch D11`, a `docs/mvp-spec.md` section, a ticket ID — each is globally unique, greppable, and outlives the delivery. `(Decision 3)`, `(item 4)`, `(step 2)` are none of those: they point into one plan file the comment never names, and every plan numbers its own decisions from 1, so the same parenthetical means something different in each. The reader who chases one lands in a record of what was argued during one delivery, which is the wrong source for why the code is shaped this way today. **The reason itself belongs in the comment** — if a sentence still reads correctly with the parenthetical deleted, the parenthetical was decoration; if it doesn't, the sentence was incomplete.
- **A comment's form follows the symbol's visibility.** A comment documenting an exported symbol is a `/** */` doc comment; comments on non-exported declarations and inside function bodies are `//`. Editors surface only `/** */` at a call site, so a caller obligation written as `//` above an export is a contract only readers of the defining file ever see — `canActOnLeague`'s "pass a `useAppNow()`-derived now, never a local `Date`" sat one function below `leagueHasStarted`'s `/** */` for exactly that reason, and every call site was free to violate it in good faith. Corollary: a comment above an export that is really about *how the body works* moves into the body rather than converting — the doc comment belongs to the caller, not the implementer.
- **A module header states a whole-module why, or the file has none.** A header earns its place only when the module as a whole carries something no single export can — a package invariant (`packages/scoring` is I/O-free), a barrel's deliberate omissions, a cross-file coupling, a single-home rule. Headers are never mandatory and never a contents listing: a header on a module with no whole-module why can only restate the filename or inventory the exports, which is a second copy of the module no compiler keeps honest and is wrong the first time something is added or re-exported.
- **Where a decision gets recorded is a ladder, not a habit.** An **ADR** when the choice constrains work beyond the file it's made in, or deviates from / extends the locked docs. A **code comment** (citing durable identifiers, per the rule above) when the why is local to the surface it shapes. A **`docs/` page** when it's operator knowledge — how to run, drive, or verify something. **Nothing at all** when the code already states it. Without a stated ladder each author records by habit, and every failure mode costs the same thing: rationale lands in a plan file that closes with its delivery, or a local choice mints an ADR that buries the real ones among trivia, or the why lands nowhere and gets re-litigated from scratch at the next touch.
- **Comment density has no quota.** The why-rule above is the only density rule: a comment earns its place by stating a why, and a non-obvious constraint must be stated somewhere. No file is flagged for looking sparse or dense as such — only for a comment that narrates, or a constraint left unwritten. A density bar in either direction is a target authors hit by padding with narration or by deleting load-bearing whys to fit; density is an output of the why-rule, never a goal.
- **The spec is the test plan.** Every scoring rule and edge case in `docs/mvp-spec.md` has a table-driven unit test in `packages/scoring` — a spec rule without a test case is a review failure. Integration tests (in-process Hono against real Postgres) cover what units can't: transactional lock validation, spread-staleness 409s, visibility filtering, join cutoffs and caps, settlement idempotency (run twice, assert identical state), override precedence. E2E (Playwright) runs the full local stack with `SimulatedProvider` + the simulated clock — no network mocks anywhere — and is the merge gate.
- **Extract repeated test setup into shared helpers** rather than copy-pasting fixtures — a copied fixture means one schema change breaks twenty test files at once and each gets repaired slightly differently; prefer table-driven tests (`it.each`) when cases differ only in inputs/outputs.
- **Assert the outcome, never the process.** A test earns its place by failing when the product breaks and staying silent when it merely changes. Concretely, at every level: assert *what the member ends up with* — the standings total, the refusal code, the pick that did or didn't persist — not the steps that produced it, the internal call sequence, or the shape of the thing displaying it. The failure mode this exists to prevent is the test suite becoming a veto on redesign: a rewording or a re-layout that breaks fifty assertions teaches the team to stop rewording and re-laying-out, which is the opposite of what tests are for.
- **UI tests bind to roles and semantics, never to copy or DOM structure.** Address elements by accessible role and name; never by column index, sibling position, CSS class, or exact prose. `getByRole("row", …)` and a named cell survive a redesign; `locator("td").nth(4)` and `getByText("4 more picks in — not yet revealed.")` do not. Where a value genuinely must be located positionally, give it a stable `data-testid` and bind to that — a testid is a deliberate, greppable contract with the test, which is exactly what an index into a `<td>` list is not. This is not a style preference: the visual layer is expected to change on the owner's judgement alone, and tests must not tax that.
- **E2E covers journeys, not branches.** Playwright's job is to prove the whole stack agrees — SPA → API → Postgres → settlement → back — on the handful of paths that must never break. Every rule that can be pinned lower *is* pinned lower: scoring in `packages/scoring`, refusals and locking in the API integration tests. A branch reachable from a unit or integration test does not earn a browser. Breadth in E2E costs wall-clock on every merge and buys coverage the cheaper layers already hold.
- **Don't unit-test presentation policy.** Helpers that decide what a screen *shows* (visibility, enablement, label strings) are the owner's call to change and shouldn't be frozen by tests. Test the rules underneath them — who may pick, what scores, what the API refuses. A helper that computes a *domain* answer is fair game; one that computes a *layout* answer is not.
- **Mobile-first.** Design and verify layouts at phone width first, then scale up — a layout squeezed down from desktop breaks at the width where nearly every pick actually gets made. All kickoff times and deadlines display in the user's local timezone; standings show a "last updated" timestamp; the UI never claims real-time freshness, because the numbers arrive on an ingestion job's schedule and a freshness claim the data can't keep is worse than a visibly stale one.
- **One page skeleton.** The authed shell owns the page column (centered `max-w-5xl`); a route renders `<main className="flex flex-1 flex-col gap-4 p-4 sm:p-6">` inside it and never sets its own outer width or horizontal padding. Deliberately narrow content (auth, wizards, empty states) is a centered card *inside* that column, not a narrower page. Loading/error/empty states center with `py-8`. A new page starts from an existing route's skeleton — layout novelty is a review flag, not a style choice, because a route that sets its own width shifts the column under the member as they navigate and re-opens a question already settled.
- **Loading a view renders skeletons, not a "Loading…" line.** A query-backed view waits behind `Skeleton` placeholders (`apps/web/src/components/ui/skeleton.tsx`) shaped like the content coming — rows for a table, a card for a card — so the layout doesn't jump when data lands. It goes through `QueryState`, which owns the loading/error/empty triad; a hand-rolled `isPending && <p>…</p>` is the drift that rule exists to prevent (LNCH-8 retrofits the sites that predate it). A placeholder must still **announce itself** (`role="status"` and an accessible label): a grey box says nothing to a screen reader where the text did. This is about *data arriving*, not an action in flight — a pending mutation disables its own control per the async-buttons rule below and never swaps content for a skeleton.
- **Async buttons: disable in place, scoped to the action.** While a mutation is pending, disable exactly the controls that trigger *that* action instance — row-level actions scope by `mutation.variables`, not a list-wide flag, which would disable rows the member never touched — and never swap the label text ("Save" stays "Save"), because a label that changes width moves the button out from under the cursor mid-click. Outcome feedback is the toast (per the errors rule) plus the query refetch; no per-button spinner text.
- **Theme tokens only.** No arbitrary color values in components — CSS-variable tokens so light/dark both work. Sole exception: third-party brand-mandated colors (OAuth buttons), with the guideline cited in a comment.
- **Accessibility:** semantic HTML, labelled controls, keyboard-operable interactions, sufficient contrast — an unlabelled control has no name for a screen reader to announce and a `div` with an `onClick` can't be reached by keyboard at all, which is a member who cannot make a pick.
- **Errors are handled,** not swallowed. User-facing failures show a clear message; server failures are logged with context; job endpoints return non-2xx on failure so the cron scheduler's failure notifications fire (ADR-0007 — no in-app alerting). In the SPA, **a failed action toasts and a failed view does not.** A mutation is something the member did, so its failure surfaces via the shared sonner toast (`toast.error`) — one mechanism, every action, no bespoke error UI. A *query* failure is not an action: it means content couldn't load, and it belongs in the space that content would have occupied, via `QueryState`'s inline message + Retry. Never both for the same failure — a toast auto-dismisses, so pairing them means the persistent load failure keeps an inline message the member can act on while a duplicate notification expires beside it. The one query that still toasts is the one with no inline home: a *background* query whose failure changes what a control does rather than what a view shows (the settings editor's pick-summary, whose absence would otherwise silently downgrade a destructive-save warning). That is the test — is there a rendered region this failure belongs in? — not "is it a query".
- **Forms use TanStack Form**, with one carve-out. SPA data-entry forms are built on `@tanstack/react-form` — no hand-rolled `useState`-per-field forms, no react-hook-form, because each hand-rolled form reimplements dirty tracking, validation timing, and error wiring, and every copy gets the label/error a11y association slightly different. **Carve-out: a form that assembles one all-or-nothing payload across mutually exclusive per-mode fieldsets** (`leagues/new.tsx`, `settings-section.tsx`) stays on plain `useState`. Splitting those between TanStack Form's field API for the mode-agnostic inputs and controlled state for the per-mode ones would fragment dirty-tracking and the single Save across two paradigms, and every field is re-validated as one assembled object through `LEAGUE_SETTINGS_SCHEMAS` at save time regardless — which is the validation guarantee the rule exists to get. This is the whole exception; a new form outside it uses the library. Field validators are the shared Zod schemas from `packages/schemas` passed directly (Zod v4 is Standard Schema — no resolver shim, no restated rules). Per-field Label/Input/error a11y wiring goes through `FormTextField` (`apps/web/src/components/form-field.tsx`); server-side field conflicts (e.g. username 409) map to field errors via `form.setErrorMap`, everything else follows the toast rule.
- **Derived user-display values have one home.** Formatting derived from user/session data (display name fallback, initials, and the like) lives in shared helpers (`apps/web/src/lib/user.ts`), never inline in components — inline copies drift.
- **User identity renders through `UserIdentity`** (`apps/web/src/components/user-identity.tsx`) — display name primary, `@username` secondary, never a bare email on a league-facing surface. A new surface showing another member reuses it rather than hand-rolling avatar/name markup.
- **Extensionless relative imports.** The repo resolves with `moduleResolution: "bundler"` and every runtime path goes through a transpiler (tsx/vite/vitest/esbuild) — never write NodeNext-style `.js` suffixes on relative imports. The suffix names a file that doesn't exist in the repo, so it resolves only where a tool volunteers to rewrite it, and each tool in the chain decides that for itself.
- **Match surrounding code** in naming, structure, and idiom. Consistency over personal preference: a file carrying two idioms makes every reader decide which one is current, and in a repo this heavily agent-authored it is also the file that teaches the next diff the wrong pattern.
- **Prefer the latest stable versions.** Upgrade when there's no breaking change; call out and schedule breaking upgrades rather than silently pinning old — a silent pin doesn't defer the upgrade, it accumulates it, and the deferred majors arrive together as unplanned migration work on the day a security fix ships only on the newest one.

## Security

- Job endpoints require the shared-secret header. Sim endpoints require an admin session **and** are not registered when the simulator is disabled (ADR-0011) — the secret header is a jobs-only mechanism. A route that was never registered can't be reached by a bug in an auth check, and a reachable sim endpoint in production would move real members' clock and results.
- **Admin capability = the `admin` role in `users.app_role`**, checked server-side against the database (ADR-0013). Granted only by a direct database update — no env-var allowlist, which grants by a string that can only be revoked by a redeploy — and no application code writes the column except `deleteAccount` clearing it. Admin surfaces are invisible to non-admins.
- Secrets and DB access are server-only; nothing secret ships in the SPA bundle — anything in the bundle is public by construction, whatever the UI does with it. No PII beyond what OAuth provides.
