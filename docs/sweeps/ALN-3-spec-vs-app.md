# ALN-3 — Spec-vs-app diff

**Date:** 2026-08-23 · **Base:** `staging` @ `ab538ed` · **Scope:** every rule in `docs/mvp-spec.md` (modes, league lifecycle, visibility, commissioner powers, settlement, screens, freshness, simulator), every decision in `docs/architecture.md`'s log (D1–D15 plus the named sections), and every ADR (0001–0043), each marked **matches** / **differs** / **not implemented** against the code on `staging`.

This is the report ALN-4 triages. No doc was edited and no code was changed. Per the epic header, **the app wins** for product differences — every `differs` row below carries the owner's question: intended (doc moves in ALN-5) or bug (task to the owning epic)?

**Method.** Six parallel read-only surveys (identity, league lifecycle, discovery/screens, UI time & display conventions, jobs/ingestion, simulator/admin), each verdict confirmed by opening the implementing file. The risk areas — `packages/scoring`, settlement orchestration, lock/visibility, the pick window, override precedence — were verified directly in the main session, not delegated. Runtime behavior is pinned by the existing simulator-backed e2e journeys and the integration suites rather than a fresh hand-drive; ALN-1 independently confirmed zero time-and-locking violations, which this sweep corroborates.

## Headline

**The product rules are implemented as written.** Both shipped modes conform to their spec sections rule by rule: Pick'em's atomic immutable submission, fixed 0.5 push, spread handshake, per-game locking, shared ranks; Survivor's change-until-kickoff, tie-advances-with-team-consumed, cancellation-returns-the-team, missed-pick elimination, all-eliminated revival, sole-survivor conclusion with co-winners; visibility filtered in the query layer everywhere; every ADR-recorded amendment is in the code it amended. March Madness is **not implemented** in full, by plan (epic 07, gated by LNCH-12 on both client and server — `packages/schemas/src/league-mode.ts:26`, `apps/api/src/services/leagues/crud.ts:70`).

The one finding that matters most is not a rule at all but a **promise**: production syncs scores every **15 minutes** while both locked docs still promise **~5 minutes** — an unrecorded change (P1). The rest of the differences split into a handful of genuine product questions (P2–P10), a set of deliberate app extensions the spec never absorbed (E1–E5), and a docs-staleness list that needs no verdict beyond "the doc moves" (S1–S9).

## Product questions for the owner (each needs a verdict)

**P1 — Score freshness: 15 minutes configured, ~5 promised.** `nfl-sync-scores` runs `*/15 * * * *` per `docs/runbooks/jobs.md:74` and the in-app operator guide (`apps/web/src/routes/_authed/guide.tsx:78,153`), but `docs/mvp-spec.md:20,237,287` and `docs/architecture.md:10,231,239` all promise ~5-minute freshness, and the runbook contradicts itself (its `JOB_SECRET` rotation step still says "≤5 minutes"). The change landed in commit `27bdbb1` (2026-08-09) editing only the runbook line — no ADR, no spec amendment. Nothing in code encodes a cadence. **Question:** keep 15 minutes (docs move — spec freshness language, architecture jobs table and design constraint, runbook self-contradiction) or restore the 5-minute cron? *Recommend: keep 15 and amend — friends-scale, cost-conscious, and nobody has complained; but this is the one row that changes a user-facing promise, so it is the owner's call, and either answer wants recording (ADR or spec amendment) since it deviates from the locked text.*

**P2 — Survivor has no provisional in-progress reading.** Spec §Provisional pick standing gives straight-up wording ("up 4") and reads mode-agnostically; Survivor is straight-up (ADR-0026), yet a Survivor pick shows only a "Your pick" pill while its game is in progress — `survivorProvisionalOutcome` returns null for anything non-final (`apps/web/src/lib/survivor-game.ts:36-46`, `survivor-game-row.tsx:344-356`). Pick'em implements the rule fully, from the same `pickMargin` settlement grades on. **Question:** was the provisional reading meant to be Pick'em-only (doc scopes it) or is this a gap (task to epic 06)? *Recommend: doc scopes it — a Survivor pick's stake is survive/die, not a margin, and "up 4" adds little; but it is a real absence the spec text currently promises.*

**P3 — Survivor shows a client-derived outcome badge on final-but-ungraded games.** Spec §Settled pick margin: "a game that has ended but whose pick has not graded yet shows nothing." Pick'em obeys (keyed on the grade's existence, `apps/web/src/lib/pickem-game.ts:39-40`). Survivor deliberately does the opposite — a final game's badge is derived client-side before settlement runs (`survivor-game.ts:9-25`, from owner-feedback item FB-23). **Question:** confirm FB-23 as the standing rule for Survivor (doc gains the mode split) or align Survivor to the wait-for-grade rule? *Recommend: keep the app — FB-23 was the owner's own ask; the doc sentence needs a Survivor carve-out.*

**P4 — Other members' pre-kickoff pick counts are disclosed.** Spec §Pick Visibility: before kickoff only the picking member sees their own pick. The pick rows themselves are filtered in the query layer (correct), but the week read serializes `hiddenPickCount` per member (`apps/api/src/services/pickem/picks.ts:361`), so everyone sees *how many* picks a rival has in before kickoff — while `getPickemPickSummary` is commissioner-gated citing exactly that leak as its reason (`picks.ts:390-394`). The spec is silent on the *fact* of a pick vs its content. **Question:** is count disclosure intended (doc states it; the internal rationale on the summary gate gets reworded) or should the count be withheld pre-kickoff? *Recommend: keep — "4 more picks in, not yet revealed" is load-bearing UI and discloses no selection; the spec gains a sentence.*

**P5 — Discovery shows an absolute start date, not the start week.** Spec §Public Discovery: each entry shows "start week (or tournament year)". The DTO carries `startsAt` only (`packages/schemas/src/discovery.ts:56`) and the card renders "Starts 9/4/26, 8:20 PM" (`apps/web/src/routes/_authed/discovery.tsx:188`). **Question:** intended (doc says start date) or should the card name the week? *Recommend: keep the app — a date answers "when do I need to have joined" better than "Week 1"; doc moves.*

**P6 — The weekly leaderboard carries no "last updated" stamp.** Spec §UI conventions: "standings pages show a last updated timestamp." The season board and survivor board both do; the weekly board on League Picks consumes the same standings query but never renders `lastUpdatedAt` (`apps/web/src/components/league/pickem-week-detail.tsx`). **Question:** does the weekly leaderboard count as a standings page (small fix, epic 05 owner) or not (doc scopes the stamp to the boards on league home)? *Recommend: add the stamp — the data is already in the response, and the weekly board is where scores are watched mid-day.*

**P7 — Survivor has no "All Picks" sibling.** Spec §Screens makes pick entry and week/pick detail sibling week-scoped sections, described mode-generically; the League Picks tab renders only for Pick'em (`routes/_authed/leagues/$leagueId/route.tsx:88-93`). Survivor's all-members view is the board on league home (pick history revealed per kickoff — the same information, differently shaped). **Question:** intended (doc scopes League Picks to Pick'em, names the board as Survivor's equivalent) or build a Survivor week detail? *Recommend: doc scopes it — the board already answers the question week-by-week and a second week-scoped Survivor surface would duplicate it.*

**P8 — Nightly reconciliation skips concluded seasons.** Spec §Data Freshness: the nightly pass "re-verifies all results and standings." `settleSweep` recomputes **active** league seasons only (`apps/api/src/services/settlement.ts:170-175`) — deliberate and documented in code (ADR-0030's cost bound), with the status-blind admin rebuild as the remedy. A correction to a concluded season's game that nobody picked will never be swept in automatically. **Question:** accept the bound (doc says "all active leagues") or widen the sweep? *Recommend: accept — the code comment already names the widening as the fix if it ever bites.*

**P9 — Account deletion is blocked by concluded leagues too.** Spec: blocked while last commissioner of any non-empty **active** league. The guard deliberately does not filter on status (`apps/api/src/services/users.ts:194-201` — a concluded league is renewable and renewal is commissioner-only), so the code is stricter than the spec. Related reading worth confirming: "non-empty" is implemented as *has other members*, so a sole-commissioner-sole-member league does not block (consistent with ADR-0004's leave rule). **Question:** confirm both readings (doc moves) or relax the guard to active-only? *Recommend: keep the app on both — the renewability rationale is sound.*

**P10 — Admin page lacks the standings-rebuild and settle-sweep triggers.** Architecture §Manual Sports Data Overrides promises "job triggers, standings rebuild"; `POST /admin/leagues/:id/rebuild` and `POST /admin/jobs/settle-sweep` exist and are gated correctly, but no SPA control calls either (`apps/web/src/components/admin/sync-jobs-card.tsx` lists only the four NFL syncs) — both are curl-only today. The seasons/weeks browser the same sentence names was removed by owner decision 2026-08-22 (`routes/_authed/admin/route.tsx:13-18`). **Question:** add the two buttons (task to epic 04) or accept curl-only (architecture text moves)? *Recommend: add the rebuild button at least — it is the named remedy for P8 and for override corrections on concluded seasons, and an admin reaching for it mid-incident shouldn't need a terminal.*

## Deliberate extensions the spec never absorbed (recommended verdict: doc moves)

These are app behaviors that go beyond the spec's text, each implemented deliberately (most with recorded reasoning). Listed for confirmation, not debate — the recommended verdict for all five is "keep the app, doc moves."

- **E1 — `maxMembers` is commissioner-configurable** (2–100, default 10; DB check constraint, pre-start editable). The spec fixes league size at "2 minimum, 100 maximum" and names no setting (`packages/db/src/schema/leagues.ts:44,55`, `crud.ts:246-254`).
- **E2 — Visibility is editable pre-start** via `EDIT_VISIBILITY` (`packages/schemas/src/league-actions.ts:38`); the spec's commissioner powers table has no visibility row. Locked at start like settings.
- **E3 — Odds and stats syncs price the current week plus the next**, matching ADR-0036's pick window (SIMP-16, `apps/api/src/services/nfl/target-weeks.ts:56-83`); architecture says "current week."
- **E4 — Overridable game fields include `period`/`clock_seconds`, and `override_status` admits all five statuses** including `in_progress` (DATA-8; `packages/db/src/schema/sports.ts:187-188`, `packages/schemas/src/game-status.ts:3-16`); architecture lists four fields and four statuses. Plus an `OVERRIDE_UNLOCKS_GAME` guard the doc doesn't name (`admin-overrides.ts:126-133`).
- **E5 — Smaller display deltas:** a `Yesterday <t>` bucket for still-scheduled games (`lib/format.ts:60`, reasoned in its test); league start lines are always absolute (`lib/league.ts:96-102`); the results segment's in-progress row is the one literal "Live" (`nfl-matchup-results.tsx:69`, dated by its column caption); discovery's creation tiebreak is newest-first where ADR-0037 stated no direction (`services/discovery.ts:114`); display name carries an app-chosen 1–50 bound; dashboard pick-status pills are a superset of the spec's three states.
