# ELM-2 — migration 0024, and proof of its data statement

`packages/db/migrations/0024_brave_thunderball.sql`, generated by
`pnpm --filter @picksleagues/db generate` with one hand-added data statement.
It carries out ADR-0026 (Survivor is straight-up only):

```sql
ALTER TABLE "survivor_picks" DROP COLUMN "spread_at_pick";
UPDATE "league_seasons" SET "settings" = "settings" - 'pickType'
  FROM "leagues"
 WHERE "leagues"."id" = "league_seasons"."league_id"
   AND "leagues"."mode" = 'survivor';
```

**Why a column created one migration earlier is dropped by the next**, rather
than editing `0023` in place: the decision landed between the two, and rewriting
an already-applied migration leaves every database that ran `0023` silently
drifted from the schema Drizzle believes it has. A redundant pair of statements
is cheap; a drifted database is not.

## Proving the data statement

The `ALTER` is covered by every `pnpm test:integration` run, which migrates a
fresh database. **The `UPDATE` is not** — the test database has no Survivor rows
predating the change, so the statement runs against zero rows there and proves
nothing. ELM-1's `pickType` key is nonetheless in real stored settings, so the
statement was exercised directly against rows shaped the way ELM-1 wrote them,
inside a transaction that rolls back.

```
BEGIN
INSERT 0 2      -- one survivor league, one pickem league
INSERT 0 2      -- a league_seasons row each, both carrying pickType

--- BEFORE: both rows carry pickType ---
   mode   | has_pick_type
----------+---------------
 pickem   | t
 survivor | t

UPDATE 1

--- AFTER: survivor stripped, pickem untouched ---
   mode   | has_pick_type
----------+---------------
 pickem   | t
 survivor | f

--- AFTER: the survivor blob still holds everything else ---
 {"endWeek": {"type": "regular", "number": 18}, "startWeek": {"type": "regular", "number": 1}, "pushTieResolution": "advance"}

ROLLBACK
```

Three things this pins, each of which a careless statement would have got wrong:

- **`UPDATE 1`, not 2** — the join to `leagues` scopes the strip to Survivor. Pick'em
  keeps its own Pick Type, and a statement that dropped the mode predicate would
  have silently deleted it.
- **The Pick'em row still reports `has_pick_type = t`** after the statement, which is
  the same fact asserted from the other side.
- **The Survivor blob keeps `startWeek`, `endWeek`, and `pushTieResolution`** — the
  `jsonb - text` operator removes one key rather than replacing the object.

The dev database was unchanged by this check: the transaction rolled back, and
the league count was the same before and after.
