# Epic: Owner Feedback (FB)

Items the owner raised from real use of the app rather than from the spec. None
of them block launch — that is why the epic sits after `09-launch` in the build
order — but each is a thing the owner noticed and wants fixed once the product
is out. Numbering follows the order they were raised, so an item stays traceable
to the round it came from.

One of these is a **question before it is a change** (FB-2): the deliverable is
a written answer with evidence, and code only if the answer calls for it.

- [ ] **FB-1** — Team logos are missing on the 2025 replay fixture. Establish which layer drops them before changing anything: the replay capture already carries logos through from `espn.fetchNflTeams()` keyed by provider team id and nulls them only when the listing lacks that team (`apps/api/src/services/sim/replay.ts`), while the hand-authored scenarios synthesize logo URLs from the abbreviation (`services/sim/scenarios/teams.ts`) — so a replay-only symptom points at the listing lookup, and a symptom on both points at the surface that renders them. Fix where the fault actually is; a fixture patched by hand would hide a live-sync bug rather than prove one isn't there. _(deps: none)_
- [ ] **FB-2** — Audit database query performance, settlement first. The target the audit is written against is **dozens to low hundreds of leagues settling in the same window**, not internet scale — an audit without a stated bound has no pass mark and will either over-engineer or clear anything. Establish whether settlement's load-inputs → persist → rebuild-standings path is per-league set-based or degrades into per-member/per-game round trips, whether the indexes its hot predicates need exist, and how long a full `settle-sweep` takes at that bound. Deliverable is the measurement plus whatever the measurement justifies. Ref: arch D10; `apps/api/src/services/settlement.ts`. _(deps: none)_
- [ ] **FB-3** — _(wontfix — owner scrapped 2026-08-09: complexity above the feature's gain for a friends-scale app)_ Standings movement for Pick'em: show each member's change in rank against the previous week's standings, so the board reads as a race rather than a snapshot. **Derived at read time, never stored** — arch D10 makes standings recomputable from (picks, results, settings), and a persisted delta column is exactly the state a full recompute would not reproduce. The prior week's standings are already reproducible from the same inputs. Ref: spec §Screens. _(deps: none)_
- [ ] **FB-4** — Scheduled dependency updates, automated. The engineering rules already require preferring latest stable (§Quality), which today depends on someone remembering; the failure that automation prevents is the one the rule names — deferred majors arriving together on the day a security fix ships only on the newest. Explore the options (Renovate vs Dependabot, grouping, auto-merge on green) and pick one. GitHub Actions minutes are free on this public repo, so cadence is a noise question, not a cost one. _(deps: FND-8)_
- [ ] **FB-5** — Drop the week selector from the standings on the league overview and show the latest standings only. Weekly performance is already reachable — League Picks has its own week selector and shows the week in more detail than the overview ever could — so the overview's selector is a second way to ask the same question, on the page least suited to answering it. Removing it simplifies the page, which is the point. Ref: spec §Screens. _(deps: none)_
- [ ] **FB-6** — Guard a commissioner against accidentally demoting themselves. A commissioner who demotes the last commissioner (or themselves generally) cannot undo it from the UI, which is what makes this worth a confirmation the other member actions don't get. **Check the pattern before adding one:** the app's existing destructive-action treatment is what this should match, so if a modal is not what the app already does elsewhere, propose what it does instead rather than introducing a second idiom. Ref: spec §Membership. _(deps: none)_
- [ ] **FB-7** — _(wontfix — owner scrapped 2026-08-09: superseded by the broader complexity-vs-value sweep, which carries the playoff question as one candidate among many)_ Decide whether Pick'em playoff support earns its complexity, or should be cut. This **reopens a settled decision**: ADR-0007 (2026-07-22) put playoffs in scope, and SIMP-17's season-range presets carry it as the Postseason and Full Season options. The question is whether any real league will use it — a playoff Pick'em league is a four-week league with slates of 6/4/2/1 games, and the whole of the support is the week-ordering and short-slate handling that already exists. So the honest framing is not "what does it cost to keep" but "what would we delete": the presets collapse to Regular Season only, matching Survivor. Answer first, with the deletion scoped; an ADR superseding ADR-0007 plus a spec amendment only if the answer is to cut. _(deps: none)_
