# Epic: Owner Feedback (FB)

Items the owner raised from real use of the app rather than from the spec. None
of them block launch — that is why the epic sits after `09-launch` in the build
order — but each is a thing the owner noticed and wants fixed once the product
is out. Numbering follows the order they were raised, so an item stays traceable
to the round it came from.

One of these is a **question before it is a change** (FB-2): the deliverable is
a written answer with evidence, and code only if the answer calls for it.

- [x] **FB-1** — _(resolved 2026-08-10: the stored replay fixture predated the logo carry-through commit — re-importing the season heals it (proven on dev, 0/32 → 32/32 logos); no live-sync bug; regression test added in `sim-replay.test.ts`)_ — Team logos are missing on the 2025 replay fixture. Establish which layer drops them before changing anything: the replay capture already carries logos through from `espn.fetchNflTeams()` keyed by provider team id and nulls them only when the listing lacks that team (`apps/api/src/services/sim/replay.ts`), while the hand-authored scenarios synthesize logo URLs from the abbreviation (`services/sim/scenarios/teams.ts`) — so a replay-only symptom points at the listing lookup, and a symptom on both points at the surface that renders them. Fix where the fault actually is; a fixture patched by hand would hide a live-sync bug rather than prove one isn't there. _(deps: none)_
- [x] **FB-2** — _(resolved 2026-08-10: full `settle-sweep` at the stated bound — 8 active league seasons, 144 league-weeks, 6,048 results — completes in ~0.6s locally (~75ms/season); nothing to fix; measurement in `docs/evidence/test-results/FB-2/`)_ — Audit database query performance, settlement first. The bound the audit is written against is **a handful of leagues settling in the same window** (SWP-7 shrank it from "dozens to low hundreds" — the real audience, not internet scale; an audit without a stated bound has no pass mark and will either over-engineer or clear anything). At that bound the audit collapses to **one timing of a full `settle-sweep` against a realistically sized dev dataset** — fix only what that measurement shows, which is plausibly nothing. Deliverable is the measurement plus whatever the measurement justifies. Ref: arch D10; `apps/api/src/services/settlement.ts`. _(deps: none)_
- [x] **FB-3** — _(wontfix — owner scrapped 2026-08-09: complexity above the feature's gain for a friends-scale app)_ Standings movement for Pick'em: show each member's change in rank against the previous week's standings, so the board reads as a race rather than a snapshot. **Derived at read time, never stored** — arch D10 makes standings recomputable from (picks, results, settings), and a persisted delta column is exactly the state a full recompute would not reproduce. The prior week's standings are already reproducible from the same inputs. Ref: spec §Screens. _(deps: none)_
- [x] **FB-4** — _(wontfix — owner declined 2026-08-10: not wanted at the moment)_ Scheduled dependency updates, automated. The engineering rules already require preferring latest stable (§Quality), which today depends on someone remembering; the failure that automation prevents is the one the rule names — deferred majors arriving together on the day a security fix ships only on the newest. Explore the options (Renovate vs Dependabot, grouping, auto-merge on green) and pick one. GitHub Actions minutes are free on this public repo, so cadence is a noise question, not a cost one. _(deps: FND-8)_
- [x] **FB-5** — _(resolved 2026-08-10: overview shows the season board only; selector, `week` search param, and dead client week plumbing removed; ADR-0035 + spec §Screens amended)_ — Drop the week selector from the standings on the league overview and show the latest standings only. Weekly performance is already reachable — League Picks has its own week selector and shows the week in more detail than the overview ever could — so the overview's selector is a second way to ask the same question, on the page least suited to answering it. Removing it simplifies the page, which is the point. Ref: spec §Screens. _(deps: none)_
- [x] **FB-6** — _(resolved 2026-08-10: self-demotion gets the app's AlertDialog confirmation ("Step down as commissioner?"); demoting another commissioner stays one click since the actor can reverse it; server ≥1-commissioner guard was already in place per ADR-0004; the Leave button shares the sole-commissioner disable-with-reason so no surface confirms a leave the server must refuse)_ — Guard a commissioner against accidentally demoting themselves. A commissioner who demotes the last commissioner (or themselves generally) cannot undo it from the UI, which is what makes this worth a confirmation the other member actions don't get. **Check the pattern before adding one:** the app's existing destructive-action treatment is what this should match, so if a modal is not what the app already does elsewhere, propose what it does instead rather than introducing a second idiom. Ref: spec §Membership. _(deps: none)_
- [x] **FB-7** — _(wontfix — owner scrapped 2026-08-09: superseded by the broader complexity-vs-value sweep, which carries the playoff question as one candidate among many)_ Decide whether Pick'em playoff support earns its complexity, or should be cut. This **reopens a settled decision**: ADR-0007 (2026-07-22) put playoffs in scope, and SIMP-17's season-range presets carry it as the Postseason and Full Season options. The question is whether any real league will use it — a playoff Pick'em league is a four-week league with slates of 6/4/2/1 games, and the whole of the support is the week-ordering and short-slate handling that already exists. So the honest framing is not "what does it cost to keep" but "what would we delete": the presets collapse to Regular Season only, matching Survivor. Answer first, with the deletion scoped; an ADR superseding ADR-0007 plus a spec amendment only if the answer is to cut. _(deps: none)_

Round 3 — raised 2026-08-10 from staging testing, after round 2 (PR #78). Same
convention: IDs record raise order, list order is priority order.

- [~] **FB-23** — A Survivor pick whose game has gone final shows no result, with the note "This week hasn't been graded yet…" (`survivor-game-row.tsx` `ungradedNote`). The *why* is real product behavior, not a simulator artifact — Survivor settles week-atomically (ADR-0025: missed-pick elimination and revival are whole-week answers) — but the member's experience is a completed pick that looks unacknowledged. The window unlock (ADR-0036) already derives win/tie from the game's terminal state instantly, so the row can show the same **derived, provisional outcome** ("Won — grading finalizes when the week completes") without waiting for settlement or violating arch D10 (display derivation, nothing stored). Separately: the owner saw the note persist after advancing to week 2 in the sim — likely the advance-then-sync two-step (grading runs on `sync-scores`/settle, not on the clock moving); verify that's all it was, and consider whether the sim page should say so. _(deps: none)_
- [~] **FB-21** — Success toasts feel like they block bottom-of-screen actions and last too long. Two parts: **duration** — nothing sets one, so every toast holds sonner's 4s default; shorten success toasts (~2–2.5s) while errors keep longer. **Placement** — the toaster is already `position="top-center"` with a header-aware offset, moved there precisely to stop bottom-bar collisions, and that commit is in staging's history — so first reproduce what the owner actually saw (stale deploy? a surface with its own bottom toast? mobile media-query fallback?) before re-fixing placement; don't churn a setting that may already be right. _(deps: none)_
- [~] **FB-20** — Weeks ahead of the pick window: keep them in the dropdown and show the week's **slate read-only** beneath a compact "not open yet" notice, instead of the bare notice card. Recommendation (owner asked): members legitimately scout ahead — Survivor is *built* on planning which teams to burn when, and a Pick'em member wants to see next week's matchups — and the slate is public schedule data, so nothing leaks (pick visibility is per-pick and untouched; the write path refuses regardless). Dropping the weeks from the selector would make the list shrink/grow over time and break linkability. Owner confirmed the direction 2026-08-10. _(deps: none)_
- [~] **FB-22** — The invites panel's empty state says "No invites yet." (`invite-panel.tsx`) even once the league has started and joining is closed — copy that promises a future the season can't deliver. When the join window is over, the empty state (and the disabled creation control's framing) should say joining is closed — e.g. "Joining is closed for this season." — rather than implying invites are still coming. _(deps: none)_
- [~] **FB-24** — Apply League Picks' mobile block treatment (FB-12: padded three-line rows on a muted background) at all widths instead of reverting to the inline single-line layout at `sm:` — the owner prefers one consistent formatting over the responsive divergence. Drop the `sm:` overrides in `PICK_ROW_CLASS_NAME` and the row's groups; keep whatever inline arrangement still reads well inside the block at desktop width. _(deps: none)_
